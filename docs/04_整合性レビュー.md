## 2. 見つけた矛盾・不備と、直し方

| # | 種類 | 内容 | 直し方（反映先） |
|---|---|---|---|
| R-1 | 不備 | 偶然との比較は「1分ごとの気配」を材料にするが、内部設計では足と気配を**表示中の銘柄についてだけ**作るように読める。表示していない銘柄で持っていた建玉の取引は比べられなくなる | 足と気配は**購読しているすべての銘柄**について作る（03 §1 candles） |
| R-2 | 不備 | 建玉を持ったままアプリを閉じると、保有の途中に空白ができる。偶然の側で「同じ長さの、空白を含まない区間」を取れないことがある | 空白の無い区間が取れない取引は**比較から外し、外した件数を出す**。比べられる件数が20未満なら「まだ判定できない」（B-2: 判定できないを断定に化けさせない）（03 review・02 1.2） |
| R-3 | 本物らしさ | 指値を「約定が突き抜けたときだけ」にすると、**最良の売り気配が買いの指値より下に来た**（本物なら自分の注文と約定している）のに約定しない | 買いの指値は「約定値 < 指値」**または**「最良の売り < 指値」で約定、売りは逆。値段は指値（Maker）。触っただけ（＝指値と同じ値）では約定しない（03 §7・05） |
| R-4 | 本物らしさと矛盾 | 「板が足りなければ残りは約定させない」は、**強制決済・損切り・利確・決済**では建玉が残ってしまい、強制決済の意味と食い違う | 決済の注文（intent=close）だけは、見えている板の最後の段の値段で残りを約定させ、知らせる。新規の注文は残りを取り消す（03 3.1・05 sweep） |
| R-5 | 本物らしさ | 待機中の注文が現金・保有を**押さえていない**。同じ保有に売りの指値を2本出すと、両方約定しうる | 待機中の注文は、買いなら「数量×値段×(1+手数料)」の現金、売りなら数量を**押さえる**（reserved）。取消・約定で戻す（03 §2 Account に reserved を足す） |
| R-6 | 曖昧 | 現物とレバで現金を分けるのか、証拠金維持率の分母・分子が決まっていない | 仮想口座は**現金を1つ**にする（GMO でレバ口座に全額を移している状態に当たる）。必要証拠金 = Σ(建値×数量)/2。維持率 = (現金 + 押さえた証拠金 + レバの評価損益) / 必要証拠金。**現物の保有は数えない**（GMO と同じ） |
| R-7 | 不備 | レバの一部決済のあと、損切り・利確の数量が元のままで、建玉より多くなる | 一部決済のたびに、付いている損切り・利確の数量を残りの数量に合わせる |
| R-8 | 本物らしさ | 同時に購読できるのは最大6銘柄だが、7銘柄目に注文・建玉ができると判定できない | 7銘柄目の**新規**注文は受け付けない（「同時に扱えるのは6銘柄までです」） |
| R-9 | 曖昧 | 振り返りの「最大DD」が何の曲線か決まっていない | **確定した損益の累計**（取引の順）の最大の落ち込み（円と%）。含み損は入らないことを画面に書く |
| R-10 | 安全 | 板の量の横棒の幅を `style` 属性で書くと CSP（`style-src 'self'`）に止められる。チャート部品も内部で `<style>` を足すなら止まる | 幅は CSSOM（`el.style.width = ...`）で入れる（属性ではないので CSP の対象外）。チャート部品が `<style>` を足すかは実装後に Playwright で CSP の違反が出ないかで確かめる。出たら `style-src` の例外ではなく部品の設定で避ける |
| R-11 | 前提の確認 | 逆指値の発火を何の値で判定するか（最終約定か気配か）を GMO は公開文書で明示していない | 最終約定で判定する（**未確認**と「このアプリについて」に書く） |
| R-12 | 本物らしさ | 注文を受け付けてから遅れの間に画面が隠れると、戻ったとき板が古い | executeAt に来たときに `isFresh()` を確かめ、古ければ拒否（「値が古いため取り消しました」） |

## 3. 設計意図との突き合わせ（分離・安全・本物らしさ）

- **分離**: 鍵・非公開 API・ワークフロー・TOKI への参照のどれも無い。端末から公開配信へ直接つなぐ。→ 満たす
- **安全**: 秘密を持たない静的サイト。注入は CSP と `textContent` で二重に止め、外部のスクリプトを読まない。受け取る値は検査する。埋め込みは描画をやめて防ぐ。→ R-10 を直せば満たす
- **本物らしさ**: 銘柄の仕様は実値。板を食う・突き抜け・円未満の扱い・遅れ・レバの規約は GMO と TOKI の実測に合わせた。→ R-3〜R-8・R-11・R-12 を直せば満たす。★残る差（分かっていて受け入れるもの）:
  - 自分の注文が板に載らないので、**自分の数量が値段に与える影響**（大口の成行で板が薄くなる等）は一度きりの約定にしか反映されない
  - 指値の**順番待ち**（同じ値段に先に並んだ注文）は数えない。突き抜け・気配の逆転で約定させるので、順番待ちで約定しない場面の多くは除かれる
  - **閉じていた間**の約定・強制決済は再現しない（分からないので、待機中の注文は取り消す）

## 4. 結論

R-1〜R-12 を内部設計の追補として下に書き、詳細設計（05）に反映する。**矛盾・不備はこの追補で解消した**ので、詳細設計に進む。

## 5. 内部設計への追補

- candles は購読中の全銘柄の1分足・1分ごとの気配を作る（R-1）
- review は空白を含まない区間だけで偶然の取引を作り、比べられない取引の件数を返す（R-2）
- 指値の約定: 買い＝約定値 < 指値 または 最良の売り < 指値。売り＝約定値 > 指値 または 最良の買い > 指値（R-3）
- sweep は intent=close のとき残りを最後の段の値段で約定させる（R-4）
- Account に `reserved = {cash, spot: {base: qty}}` を足す（R-5）
- 維持率の式を R-6 のとおりにする
- 一部決済で損切り・利確の数量を合わせる（R-7）
- 購読の上限を超える新規注文は拒否（R-8）
- 最大DD は確定損益の累計で（R-9）
- 動く幅は CSSOM で入れる（R-10）
- 逆指値は最終約定で判定（R-11）
- 約定の直前に鮮度を確かめる（R-12）

## 7. 過去の足の中継を足すときの突き合わせ（2026-09-27）

| 番号 | 突き合わせたこと | 結果と直し方 |
|---|---|---|
| R-18 | 「リアルタイムだけ」（3.2 入れないもの）と過去の足 | 矛盾しない。過去の足は**見るためだけ**で、早送りや過去の約定の判定には使わない。約定は `account` がリアルタイムの板と約定だけで決める（history → account の依存を作らない） |
| R-19 | 偶然との比較（F-6）に過去の足を使えるか | 使わない。比較は Taker の脚に最良気配（買い・売り）が要るが、過去の足には気配が無い。終値で代用すると**スプレッドのぶん偶然側が有利**になり、比較が甘くなる。これまで通り、自分で記録した気配だけで比べる |
| R-20 | N-1c「通信の経路を共有しない」と中継 | 中継は Cloudflare 上で、TOKI の GitHub Actions とは IP も経路も別。鍵を持たないので、中継が乗っ取られても実口座には届かない |
| R-21 | N-1d「自動で動く仕組みを持たない」と中継 | 中継は呼ばれたときだけ動き、定期実行は持たない。Actions も置かない |
| R-22 | N-2 と中継（第三者が使う・値の差し替え） | 許可した組み合わせ以外は断る（何でも取り次ぐ中継にしない）。取り次ぐ先は1つの URL に固定。アプリは中継の値も配信と同じ強さで検査する（数・時刻・件数の上限）。CSP の connect-src は中継の origin だけを足す |
| R-23 | N-6「止まらない」と中継の障害・無料枠切れ | 中継が失敗・遅い（8秒）・変な値のときは、過去の足なしで今まで通り動く。チャートに理由を出すだけで、注文には影響しない |
| R-24 | 個人のデータ（N-2）と中継 | 中継に送るのは銘柄・足の長さ・日付だけ。取引の記録は送らない。Cloudflare には利用者の IP が見えるので「このアプリについて」に書く |
| R-25 | 同じ分の足の重ね方 | 開いた分は途中から数え始めるので、配信の足だけでは始値・高値・安値が欠ける。始値は過去の足、高値・安値は両方の広い方、終値は配信を採る |

結論: 設計意図（分離・安全・本物らしさ）と食い違うものは無い。R-19・R-25 を詳細設計に入れて進める。

## 8. ティック足を足すときの突き合わせ（2026-09-28）

| 番号 | 突き合わせたこと | 結果と直し方 |
|---|---|---|
| R-26 | 「リアルタイムだけ」・R-18 とティック | 過去の約定も見るためだけ。約定の判定・偶然との比較には使わない（history → account の依存を作らない） |
| R-27 | 中継の許可の範囲（R-22）を広げること | 足すのは `/trades` の1つだけ。symbol は同じ15銘柄、page は 1〜10、count は 100 に固定。取り次ぎ先も1つに固定する。**中継の貼り直し**が要る（貼り直すまでは 404 → 今まで通り） |
| R-28 | ページをまたぐ間に新しい約定が入ると、ページがずれる | ずれは「古い側へ押し出される」向きだけなので、**重複は出るが抜けは出ない**。時刻・値段・数量・売買で重複を除く |
| R-29 | 同じ秒に複数の約定がある（BTC_JPY は1分に約50件） | チャートの横軸に時刻を使うと重なって描けない。横軸は通し番号にし、表示の時刻だけ約定の時刻に引き直す |
| R-30 | NT の区切りが、足が増えるたびに動かないか | `floor(seq/N)` で区切るので、新しい約定は最後の足に入るだけ。過去の約定を取り直したときだけ番号を振り直し、描き直す |
| R-31 | 記憶の量（N-4） | 銘柄ごとに5,000件まで。超えたら古い方から捨てる。端末には保存しない |
| R-32 | 閑散な銘柄（DOGE は1分に約2件）で 1,000件が何時間ぶんか | 約8時間ぶん。100T なら10本しかないが、そこから先は開いている間に伸びる。足りないことを「約定を待っています」と出す |

結論: 設計意図と食い違うものは無い。R-27 の中継の貼り直しを利用者の手順に入れる。
